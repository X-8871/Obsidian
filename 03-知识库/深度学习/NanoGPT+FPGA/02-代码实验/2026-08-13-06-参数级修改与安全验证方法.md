# 参数级修改与安全验证方法

## 文档定位

这是从原“第 4 天讲义”提炼的实验方法，不应误写成全部板级结果已经完成。资料显示当时开发板不在手边，因此编译、打包和 Python 仿真可以作为证据，但板级现象仍需复验。

## 三条安全绳

```text
备份：修改前保留可恢复基线
仿真：能在 Python 或测试台预演的先预演
基线：修改后恢复原值并重新验证已知输入输出
```

## 统一预判模板

```text
我即将修改：文件、位置、旧值 → 新值
我的预判：预期现象及原因
影响范围：需要重建哪些产物，不需要动哪些产物
成功判据：用什么输出证明预判成立
恢复判据：怎样证明已经回到基线
```

## 实验 A：行为参数修改

示例：`DEFAULT_MAX_NEW_TOKENS: 8u → 4u`。

- 预期：默认生成数量从 8 变 4，前 4 个 Token 内容不变。
- 原因：它控制循环次数，不参与模型数值计算。
- 影响：重编 PS ELF、重打 BOOT、重新烧录；不用重新生成 Bitstream。

## 实验 B：数值参数故意改坏

示例：`q_shifts[0]: 13u → 12u`。

```mermaid
flowchart LR
    A["少右移 1 位"] --> B["Q 数值约放大 2 倍"]
    B --> C["更容易饱和/截位"]
    C --> D["第 0 层 Attention 改变"]
    D --> E["误差向后传播"]
    E --> F["Token 可能分歧"]
```

程序通常不会崩溃；危险恰恰在于流程能完成但数值悄悄变坏。

## 双轨验证

| 条件 | 可完成的验证 | 正确结论写法 |
|---|---|---|
| 有开发板 | Python 预演 + 编译打包 + 板级 Token/dump + 恢复基线 | 板级结论按实际证据写 |
| 无开发板 | Python Q30 参数预演 + 编译打包 + 代码影响分析 | “Python/构建层通过，板级待验证” |

## 恢复要求

1. 把参数恢复到原值。
2. 重编相应产物。
3. 使用与修改前完全相同的输入和环境。
4. 确认 Token、状态和错误计数回到基线。
