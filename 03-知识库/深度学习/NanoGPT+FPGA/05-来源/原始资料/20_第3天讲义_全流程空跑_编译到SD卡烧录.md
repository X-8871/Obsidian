## 〇、开场总图（讲 5 分钟）：文件的"变形记"

先给用户看今天的主线——一个 `.c` 文件到板子上跑起来，中间要变几次形态：

```text
ps/src/main.c（源代码，人读）
   │  Vitis 编译（arm gcc）
   ▼
ps_mailbox_runner.elf（ARM 机器码）
   │
   │  + system_wrapper.bit（PL 配置，Vivado 产物，今天不重做）
   │  + fsbl.elf（第一阶段引导，现成）
   │  + weights.bin / scales.bin / 嵌入表.bin（模型数据，现成）
   │  bootgen 按 BIF 清单缝合
   ▼
BOOT.bin（一个文件，包含上面全部）
   │  读卡器复制到 FAT32 SD 卡根目录
   ▼
开发板上电：FSBL 启动 → 配置 PL → 模型数据写入 DDR → 运行 ELF
   ▼
UART 打印 "nanoGPT Zynq UART ready"，等你输入提示词
```

**一句话定位**：前两天是"看懂图纸"，今天是"按图纸把房子原样再盖一遍"——一块砖都不换，但每块砖都要经自己的手放上去。

✅ 复述检查点：让用户不看图回答"ELF、bit、BOOT.bin 三者谁包含谁？"——答出"BOOT.bin 包含 ELF 和 bit（还有 FSBL 和数据），ELF 由 main.c 编译来，bit 由 Vivado 综合实现来"，才继续。

## 一、解剖 BIF 清单（讲 15 分钟）：今天最有教学价值的一个文件

打开参考 BIF：`D:\FPGA\NanoGPT\deploy_current_20260808\boot\BOOT_fx2_standalone_20260809.bif`，逐段讲：

```text
[bootloader] ... fsbl.elf                          ← ① FSBL 引导程序
... system_wrapper.bit                             ← ② PL 配置比特流
[load=0x11000000] ... weights.bin                  ← ③ 量化权重
[load=0x11C00000] ... scales.bin                   ← ④ 量化 scale
[load=0x13000000] ... token_embedding_i8.bin       ← ⑤ token 嵌入表
[load=0x13010000] ... position_embedding_i8.bin    ← ⑥ 位置嵌入表
[load=0x13028000] ... token_embedding_scale_q30.bin    ← ⑦⑧ 嵌入 scale
[load=0x13028400] ... position_embedding_scale_q30.bin
[load=0x13200000] ... layernorm_coeff_q24.bin      ← ⑨ LN 系数
[load=0x13205000] ... lm_head_scale_ratio_q30.bin  ← ⑩ LM head scale
... ps_mailbox_runner.elf                          ← ⑪ PS 主程序（最后！）
```

**必讲的三个设计点**：

1. **顺序就是因果**：FSBL 必须在最前（它是上电后第一段运行的代码，负责初始化 DDR 和加载后续所有分区）；bit 在 ELF 前（先把 PL 电路配置好，PS 程序运行时硬件已就绪）；**所有模型数据在 ELF 前**（ELF 开始跑的时候，DDR 里的权重必须已经躺好了）。
2. **`[load=地址]` 与第 1 天的 `#define` 是同一份契约**：让用户拿出第 1 天笔记，亲手连线——
   - `0x11000000` ↔ `WEIGHTS_BASE`
   - `0x13000000` ↔ `TOK_EMB_I8_BASE`
   - `0x13010000` ↔ `POS_EMB_I8_BASE`
   - `0x13028000`/`0x13028400` ↔ `TOK_EMB_SCALE_Q30_BASE`/`POS_EMB_SCALE_Q30_BASE`
   - 这就是"PS 程序凭什么知道权重在哪"的答案：**不是程序找数据，是烧录时按约定地址放好的**。这是第 6 天"三处同步"的第四处（BIF）！
3. **每个 .bin 都是 Python 量化链路的产物**：回忆第七章——这些 bin 是 `01_VSCode_Python` 量化脚本从 `ckpt.pt` 生成的。BOOT.bin 是"模型 + 硬件 + 软件"三件东西的结婚照。

✅ 复述提问：Q：如果把 ELF 放在 BIF 第一行会怎样？期望答案：ELF 启动时 DDR 里还没有权重数据、PL 还没配置，程序必然跑飞——顺序错了整个系统崩。

## 三、Vivado 侧：今天不重跑，但要知道门在哪（讲 10 分钟）

今天用**既有签核 bitstream**（`artifacts\` 或 Vivado 工程 `impl_1` 目录下的 `system_wrapper.bit`），不重综合。但要带用户"认门"：

1. 工程入口：`02_Vivado_PL\open_vivado_project.ps1`，实际工程在 `fpga\nano_gpt\nano_gpt.xpr`。
2. 若将来改了 PL（第 5、6 天就会），完整链条是：**Run Synthesis → Run Implementation → Generate Bitstream → 新 bit 进 BIF**。每一步都可能几十分钟到几小时——让用户有心理预期。
3. 签名概念：当前签核 bit 的 SHA256 是 `952B6ECC...B217`（15 号文档第十节）。以后改完 PL 生成的新 bit 指纹会变，**实验记录里必须写清用的是哪个指纹的 bit**——这是区分"新旧硬件版本"的唯一可靠办法（FXF2 签名标记就是为此而生的，15 号文档第九节）。

✅ 复述提问：Q：第 4 天改 `main.c` 的 shift 表，需要重新生成 bitstream 吗？期望答案：不需要——shift 表是 PS 侧 C 代码，只重编 ELF、重打包、重烧卡即可；bit 是 PL 电路，没动 PL 就不用动它。

     -arch zynq `

## 五、SD 卡烧录与脱机启动（用户动手，15 分钟）

严格按此顺序，教学 AI 逐步等回报：

1. 确认 SD 卡是 **FAT32** 格式（属性里看）。
2. 卡上若已有旧 `BOOT.bin`，先改名备份（如 `BOOT_old.bin`）——**根目录最终只能有一个 `BOOT.bin`**。
3. 把第四节生成的 bin 复制到 SD 卡**根目录**，重命名为 `BOOT.bin`。
4. **安全弹出**（不能直接拔）。
5. 开发板**完全断电** → 插卡 → 拨码设为 **SD Boot** → 重新上电。
6. 不接 JTAG，只接 USB-UART，打开串口终端（115200，8N1）。

成功判据：串口出现 `nanoGPT Zynq UART ready` 就绪信息。

✅ 复述提问：Q：为什么必须"完全断电"而不是按复位键？期望答案方向：要验证的是冷启动全流程——FSBL 从 SD 卡加载、配置 PL、写 DDR、跑 ELF，任何一步靠旧状态蒙混都证明不了脱机能力。

## 六、UART 基线验证（用户动手，15 分钟）

1. 串口终端确认看到就绪信息和 `> ` 提示符。
2. 发送 `1:ROMEO:`。
   - **通过标准**：返回 1 个生成字符，Token ID 为 `0`（字符 `0x0A` 换行）——与 8 月 9 日 JTAG 基线完全一致。
3. 再用上位机 `host_tools\nanogpt_uart_gui\dist\KeChuangNanoGPT.exe` 发一次 `1:ROMEO:`，确认 GUI 通道也通。
4. 学有余力可加做 `8:ROMEO:` 冒烟：完整返回 8 个字符、无超时无复位。
5. 提醒协议细节（第 1 天学过）：`数字:` 是输出长度前缀，是 `uart_console` 解析的协议头，不是模型输入。

**这一步的深层意义（教学 AI 要讲）**：同样的 `1:ROMEO:` → token 0，8 月 9 日是 JTAG 在线灌出来的，今天是 SD 卡脱机跑出来的——**输入相同、输出相同、路径完全不同**，这才叫"系统真的独立了"。

## 七、排错决策树（失败时严格按序排查，禁止跳步）

| 顺序 | 检查项 | 典型症状 → 对策 |
|---|---|---|
| 1 | SD 卡格式 | 非 FAT32 → 重新格式化 |
| 2 | 文件名与位置 | `BOOT.bin` 不在根目录 / 有多个 BOOT 文件 / 名字多个空格 → 修正 |
| 3 | 拨码开关 | 不是 SD Boot 模式 → 对照板卡丝印改拨码 |
| 4 | 串口物理层 | 无任何输出 → 换 COM 口、查 TX/RX、确认共地、确认 115200 8N1 |
| 5 | BIF 路径 | bootgen 报错找不到文件 → 逐行核对 BIF 里的绝对路径（注意"副本"目录问题） |
| 6 | 启动卡死 | 有乱码或无 ready → 断电 10 秒再上电；仍不行则回退用参考 BOOT.bin 验证硬件，排除打包错误 |
| 7 | 基线不符 | token 不是 0 → **立即停**，保留现场记录，回退 14 号文档第七节流程 |

铁律：任何一步失败都**先记录现象再排错**；修好后必须从第 1 步顺序重验，不能"改了接着试"。
