## 一、给教学 AI 的总说明

### 1.1 本周任务的来源

用户的导师布置了"学会看代码、改代码"的任务。导师明确表示：**即使往坏的方向改也没问题**，重点是建立"改了能预判后果、改坏了能定位原因"的能力。本周结束后，导师可能抽查任意一个文件，用户必须能讲清它的作用并现场演示一次"改动 → 编译 → 烧录 → 验证"闭环。

### 1.2 用户当前状态（教学起点，不要重复教学）

- 已完成 nanoGPT 七章主线学习，能解释 Transformer 数据流、INT8、scale、Q30。
- 已在真实 Zynq-7020 开发板完成 JTAG 单 Token 推理（FXF2 硬件版本，签名 `0x46584632`）。
- 当前权重指纹：`0f6b6bf5376041c66704377b90fb0937e9c4774d8a139f4853b843063baa5ab7`（简写 `0f6b...5ab7`）。
- **薄弱点**：没有系统读过 PS/PL 代码；没有独立走过"改代码 → 编译 → 烧录 SD 卡"全流程；C 语言有基础但不熟位运算和寄存器操作；Verilog/HLS 几乎零基础。

### 1.3 本周总目标

```text
第 1~2 天：学会看代码（PS main.c + PL 数据流）
第 3 天：  全流程空跑（不改代码，走通 编译→打包→SD 烧录→脱机启动→UART 验证）
第 4 天：  Level 1 参数级修改（只改常量，PS 单独重编，快速迭代）
第 5 天：  Level 2 流程级修改（PS 加 CMD + HLS 算子修改并重导 IP）
第 6 天：  Level 3 结构级修改（加 debug 寄存器，PL/PS/脚本三处同步，上板验证）
第 7 天：  Level 4 入门（只到 HLS 仿真）+ 无提示独立完成一次完整改动闭环
```

Level 定义（教学时按此口径向用户解释）：

| Level | 名称 | 定义 | 本周验收深度 |
|---|---|---|---|
| L1 | 参数级 | 改 `main.c` 常量（shift 表、token 数），只重编 ELF | 上板验证 |
| L2 | 流程级 | PS 加新 CMD；改 HLS 源码并重导 IP、重生成 bitstream | 上板验证 |
| L3 | 结构级 | 改数据通路/寄存器映射，PL、PS、脚本三处同步 | 上板验证 |
| L4 | 算法级 | 改算子结构或量化格式 | **只做 HLS C 仿真 + 影响分析，不要求生成 bitstream** |

### 1.4 教学规则（每节课必须遵守）

1. **一次只给一步**。给出当前步骤后停止，等用户贴回结果（终端输出/截图描述/文件内容）再继续。禁止一次性甩出一整天的操作。
2. **先预测，后动手**。每次改代码前，必须让用户先写下"我预期会发生什么"，运行后对比。这是导师要求的核心能力。
3. **先框架，后细节**。讲任何文件前，先说明它在 `字符→Token→FPGA→字符` 总链路中的位置。
4. **只基于项目真实文件教学**，不要编造项目里不存在的文件、命令或寄存器。引用代码时给出文件路径和行号；行号可能与用户本地略有出入，让用户以内容搜索为准。
5. **英文缩写首次出现时**，给出英文全称、中文含义、本项目中的作用。
6. **用户复述通过才进入下一步**。复述错误时先纠正因果关系，不要直接给答案。
7. **改坏是计划的一部分**。L1 的"有害改动"实验是故意改坏的，不要替用户规避；重点是引导他观察现象、解释原因、恢复原状。
8. **重要改动前提醒备份**：改 `main.c`、`hls/source/`、Vivado 工程前，提醒用户复制一份原文件（文件名加 `.bak_YYYYMMDD` 后缀）。
9. **每天结束时**，提醒用户按导师要求用 Word 记录当天的：改动内容、预期、实际现象、原因分析、结论。这是硬指标。
10. **所有结论注明层级**：Python 仿真 / HLS C 仿真 / Vitis 编译 / JTAG / SD 脱机 / UART，禁止跨层级推断"通过"。

### 1.5 禁止事项

- 禁止重新教学前七章 Transformer 内容。
- 禁止直接修改 `fpga/ip_repo/` 内的 Verilog（HLS 生成物，改了会被覆盖；正确路径见第 5 天）。
- 禁止在没有任何输出证据时宣布"通过"。
- 禁止把 HLS C 仿真通过说成"板级验证通过"。
- 禁止混用旧权重/旧 DDR 镜像做验收，所有实验必须基于指纹 `0f6b...5ab7` 这一套。
- 禁止替用户做"复制粘贴以外"的动手操作——编译、烧录、串口发送都必须用户亲手执行，AI 只给命令和判据。
- 如果 8 月 10 日的部署验收（SD 脱机启动、UART 单 Token）实际未完成，**先回退执行 `14` 号文档第七节**，不要硬推本计划。第 3 天的空跑结果可以自然验证这个前提。

## 三、第 1 天（8 月 11 日）：看代码① —— PS `main.c` 硬件契约段

### 目标

用户能看着 `ps\src\main.c` 前 120 行，讲清"PS 通过什么和 PL 说话、数据放在 DDR 哪里、量化误差靠什么控制"。

### 教学步骤（AI 按序执行，每步等用户回应）

1. 先画总图：UART 输入 → PS `main.c` → 写 PL 寄存器（`PL_BASE = 0x40000000`）→ PL 算完 → PS 读结果 → UART 输出。告诉用户今天只学这张图里 `main.c` 的"常量区"。
2. 逐段讲解并提问（每段讲完让用户复述）：
   - 寄存器定义段（约 L4~L37）：`REG_CONTROL`/`REG_STATUS`/`REG_MODE` 及 `MODE_*` 各位含义。
   - DDR 地址映射段（约 L39~L59）：`LAYER_A_BASE`、`WEIGHTS_BASE`、`K_CACHE_BASE`、`MAILBOX_BASE` 等。
   - 模型维度段（约 L87~L98）：`BLOCK_SIZE=256`、`VOCAB_SIZE=65`、`D_MODEL=384`。
   - 字符表 `g_itos`（约 L100~L106）：Token ID ↔ 字符的映射。
   - shift 表（约 L108~L113）：`q_shifts`/`k_shifts`/`v_shifts`/`ffn_shifts` 等 6 层右移位数——这是定点量化控制误差的关键，必须讲透"右移 13 位 ≈ 除以 8192"。
3. 快进到函数地图（只讲签名和职责，不逐行）：
   - `wr32`/`rd32`/`barrier`（约 L115~117）——一切硬件操作的源头；
   - `uart_init`/`uart_putc`/`uart_getc`（约 L144~163）；
   - `mailbox_write`/`mailbox_read`（约 L236~244）；
   - `build_hidden`（约 L304）、`wait_done`（约 L425）、`run_attn`（约 L471）、`run_layer`（约 L489）、`run_full_model`（约 L570）；
   - `pl_lm_head_argmax_row`（约 L622）、`generate_greedy`（约 L650）——生成循环的心脏；
   - `uart_console`（约 L716）、`main`（约 L785）。

### 文件级验收（全部通过才算第 1 天完成）

| # | 验收项 | 通过标准 |
|---|---|---|
| 1 | 打开 `ps\src\main.c`，用户指出 `PL_BASE` 并口答其作用 | 答出"PL 寄存器在 PS 地址空间里的基地址，wr32 写它就是写硬件" |

## 四、第 2 天（8 月 12 日）：看代码② —— PL 数据流与 HLS 算子

### 目标

用户能画出 PL 内部数据通路图，并讲清 4 个 HLS 算子各干什么、`fpga\rtl\` 与 `hls\source\`、`fpga\ip_repo\` 三者的关系。

### 教学步骤

1. 先讲"三层楼"模型（本周最重要的认知）：
   ```text
   hls/source/*.cpp   —— 人写的算法源码（改这里）
        ↓ Vitis HLS 综合
   fpga/ip_repo/      —— 自动生成的 Verilog IP（不看细节、不手改）
        ↓ Vivado 例化连接
   fpga/rtl/*.v       —— 手写顶层：把 IP 串成链 + UART 桥（可以改，本周第 6 天改）
   ```
2. 读 `hls\source\common\hls_common.hpp`（全文仅约 18 行）：`ap_int<8>` 等定点类型、`clamp_signed` 饱和截位。提问：为什么 FPGA 不用 `int` 而用 `ap_int<8>`？
3. 依次读 4 个算子的 `.hpp` 接口和 `.cpp` 主循环（每个 10~15 分钟，只讲输入/输出/核心循环，不逐行）：
   - `tiled_matmul\tiled_matmul.cpp`：分块矩阵乘，Q/K/V/Proj/FFN 全靠它；
   - `mha_kernel\mha_kernel.cpp`：注意力打分与加权；
   - `layernorm_kernel\layernorm_kernel.cpp`：均值方差归一化；
   - `gelu_embed_kernel\gelu_embed_kernel.cpp`：嵌入相加 + GELU 激活。
   - 每个算子讲完，让用户用一句话复述"它吃什么、吐什么"。
4. 读 `fpga\rtl\hls_kernel_chain_axis_top.v`：找 4 个算子的例化位置和 AXI-Stream 连线；再读 `pl_uart_ps_bridge.v` 讲 UART 字节如何进出 PL。
5. 对照 `NanoGPT_PS+PL_重要参数汇总.md` 核对资源/时序数字，建立"代码 ↔ 报告"的对应感。

## 六、第 4 天（8 月 14 日）：Level 1 —— 参数级修改（故意改坏也没关系）

### 目标

通过"无害改动 + 有害改动"两个对照实验，让用户建立"改常量 → 预判 → 观察 → 解释 → 恢复"的反射。L1 只重编 ELF，不碰 bitstream，迭代快。

### 实验 A（无害改动）

1. 备份 `ps\src\main.c`。
2. 改 `DEFAULT_MAX_NEW_TOKENS`（约 L91，当前 `8u`）为 `4u`；或改 `MAX_NEW_TOKENS`（约 L92，当前 `200u`）为 `100u`。
3. 改之前让用户写预判："生成数量会变少，内容质量不变"。
4. Vitis 重新 Build → 重打包 BOOT.bin → SD 烧录 → UART 发送 `8:ROMEO:`。
5. **通过标准**：返回字符数按预期变化；Token ID 序列前若干个与原基线一致；用户能解释"为什么只改 PS 常量不影响模型计算正确性"。

### 实验 B（有害改动，计划内改坏）

1. 改 `q_shifts[0]`（约 L108，当前 `13u`）为 `12u`。
2. 改之前让用户写预判（AI 引导方向：第 0 层 Q 多放大 2 倍 → 注意力分布异常 → token 错乱）。
3. 同样走 编译→烧录→`1:ROMEO:`。
4. **通过标准**：返回结果与基线不同（token 不再是 `0` 或后续全乱）；用户能用 `ps\scripts\dump_layer0_hello_output.tcl` 或 `dump_context_row_stages.tcl` dump 出第 0 层中间数据，指出异常出现在哪一级；最后**恢复原值**，重编烧录，`1:ROMEO:` 回到 Token ID `0`——恢复成功才算实验 B 完成。
5. Word 记录必须包含：改了哪一行、预判、实际现象、dump 证据、原因分析、恢复验证。

### 文件级验收

| # | 验收项 | 通过标准 |
|---|---|---|
| 1 | 实验 A 全流程 | 现象符合预判，且用户说清"为什么这次不用重新生成 bitstream" |

## 七、第 5 天（8 月 15 日）：Level 2 —— 流程级修改（PS 加 CMD + HLS 重导 IP）

### 目标

上午：在 `main.c` 中仿照既有调试命令新增一个 CMD，走通"PS 功能扩展"流程。
下午/晚上：修改一个 HLS 算子，走通"改 C++ → C 仿真 → 重导 IP → 重生成 bitstream"长流程（综合实现耗时长，AI 要提醒用户利用等待时间写 Word 记录）。

### 任务 5A：PS 新增 CMD（模仿 `CMD_LAYER0_ONLY` 的既有范式）

1. 在 `main.c` CMD 定义段（约 L72~L77）新增 `CMD_ECHO_VERSION 6u`。
2. 在 `main()` 的命令分发处模仿 `run_layer0_ln1_only`（约 L575）的处理方式，新增分支：收到该命令时通过 UART 打印一行版本字符串（如 `NGPT-L2-OK`）并返回就绪。
3. Vitis Build → 打包 → 烧录。
4. **通过标准**：通过上位机或 JTAG 触发新命令后收到自定义字符串；既有 `1:ROMEO:` 基线不受影响。

### 任务 5B：HLS 算子修改（建议选 layernorm，链路最短）

1. 备份 `hls\source\layernorm_kernel\layernorm_kernel.cpp`。
2. 做一个可见但无害的改动，例如给归一化输出乘以一个固定系数（如 `* 1.0` 改成先 `+0` 再加一个可读回的调试标记，或在接口加一个输出计数器）。**AI 应根据文件实际结构选择最小改动点，改前给用户讲清影响面。**
3. 先跑 C 仿真：用 `tb_layernorm_kernel.cpp` 编译执行（testbench 的作用见第 2 天验收 #4），确认仿真通过。**C 仿真不过，禁止进入综合。**
4. Vitis HLS 综合 → 导出 IP → 整体替换 `fpga\ip_repo\layernorm_kernel\`（提醒备份原目录）→ Vivado 重新 Synthesis/Implementation/Bitstream → 重打包 → 烧录。
5. **通过标准**：tb 仿真日志通过；新 bitstream 烧录后 `1:ROMEO:` 基线 Token ID 仍为 `0`（说明改动无害）或现象与预判一致（若改动本身会改变数值）。

## 八、第 6 天（8 月 16 日）：Level 3 —— 结构级修改（三处同步，上板验证）

### 目标

完成一次"牵一发动全身"的改动：在 PL 增加一个可读回的 debug 寄存器，同步修改 PL、PS、调试脚本三处。这是导师"日后有用"能力的最集中体现。

### 教学步骤

1. 讲清"三处同步"原则：寄存器定义不是只改一处的——
   ```text
   fpga/rtl/*_hls_wrapper.v（或顶层）: 新增寄存器偏移的译码与读出逻辑
   ps/src/main.c:                       新增对应 #define（如 REG_DEBUG_COUNTER 0x8Cu）
   ps/scripts/*.tcl / host_tools:       读该地址做验证
   ```
2. 建议的最小改动方案（AI 可按实际寄存器占用情况调整偏移，但必须先在 `main.c` L4~L25 和 wrapper 中确认 `0x8C` 或所选偏移未被占用）：
   - PL：在 wrapper 寄存器组中新增一个只读寄存器，内容为内部状态计数（如完成脉冲计数或固定魔数 `0xC0DE0001`——第一版建议直接用固定魔数，降低译码错误风险）。
   - PS：`main.c` 增加 `#define` 和一个读回打印（可挂在第 5 天新增的 CMD 分支里）。
   - 脚本：新增一个 `ps\scripts\read_debug_counter.tcl`，仿照 `check_pl_uart_regs.tcl` 的写法读该地址。
3. 流程：Vivado 改 RTL → 重实现 → bitstream → Vitis 重编 ELF → 打包 → 烧录 → 三种方式交叉读回（UART 打印 / tcl 读取 / XSDB 手动 `mrd`）。

### 文件级验收

| # | 验收项 | 通过标准 |
|---|---|---|
| 1 | 用户列出本次改动触碰的全部文件清单 | 至少 3 个文件，且能说明每个文件里改了什么 |
| 2 | 三种途径读回新寄存器 | 值一致且等于预期（如 `0xC0DE0001`） |
| 3 | 既有功能回归 | `1:ROMEO:` 基线 Token ID 仍为 `0` |
| 4 | 情景提问："如果 PL 改了偏移但 PS 没改，会怎样？反过来呢？" | 答出"读错地址/读到旧数据或总线错误"，理解三处同步的必要性 |

## 十一、异常与回退预案

| 情况 | 处理 |
|---|---|
| 第 3 天空跑失败（SD 脱机/UART 不通） | 回退到 `14` 号文档第七节 P0 任务，修复后重做空跑，本周后续天数顺延 |

| 开发板/读卡器当天不可用 | 当天降级为仿真与文档任务，如实记录"硬件不可用"，禁止编造板级结果 |
