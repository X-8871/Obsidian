## 〇、开场仪式（讲 10 分钟）：改代码的三条安全绳

今天开始前，先给用户建立"安全绳"意识——以后每次改代码都是这三条：

```text
安全绳 1：备份 —— 改前复制原文件为 main.c.bak_YYYYMMDD
安全绳 2：仿真 —— 能在 Python/tb 里预演的，先在电脑上看后果
安全绳 3：基线 —— 改完无论结果如何，最后必须恢复原状并复验基线
```

再讲今天的实验设计哲学（导师原话精神）：**故意改坏不是捣乱，是解剖**。一个你亲手搞坏又亲手修好的系统，你才真的拥有它。

**预判模板**（今天起每次改代码前必须写，写进 Word 记录）：

```text
我即将修改：<文件> 第 <行>，把 <旧值> 改成 <新值>
我的预判：<运行后会出现什么现象，为什么>
影响范围：<这次改动需要重编哪些产物、不需要动哪些>
```

✅ 检查点：用户亲手完成备份：`ps\src\main.c.bak_20260811`（日期按当天），并口述"为什么要先备份再改"。

## 一、实验 A：无害改动 —— 生成数量参数（30~45 分钟）

### 改动内容（二选一，推荐 A1）

- **A1**：`DEFAULT_MAX_NEW_TOKENS`（main.c 约 L91，当前 `8u`）→ 改为 `4u`
- **A2**：`MAX_NEW_TOKENS`（约 L92，当前 `200u`）→ 改为 `100u`

### 执行流程

1. **写预判**（教学 AI 引导方向，但不要剧透答案）：不带数字前缀直接输入 `ROMEO:` 时，默认生成几个字符？改之前是 8 个，改之后应该是几个？生成内容的"质量"会变吗？
   - 期望预判：默认生成数 8→4；模型计算本身不受影响，前 4 个字符应与原基线前 4 个一致。
2. 改代码（一行）。
3. Vitis 重新 Build → 确认 0 error → 找到新 ELF。
4. 复制第 3 天的练习 BIF，改 ELF 路径 → bootgen 重打包。
5. **Track A（有板）**：烧录 SD → 脱机启动 → 直接输 `ROMEO:`（不带前缀）→ 观察返回字符数。
   - **通过标准**：返回 4 个字符；再用 `8:ROMEO:` 验证前缀仍可覆盖默认值；首 token 仍为 ID `0`。
6. **Track B（无板）**：记录"编译打包通过，板级现象待验"；转而做代码级验证——在 `main.c` 的 `uart_console`（约 L757）和 `generate_greedy`（约 L657~659）里找到默认值生效的三处证据，用自己的话讲清"`DEFAULT_MAX_NEW_TOKENS` 在什么情况下被使用、什么情况下被覆盖"。

### 必答思考题

Q：为什么这个改动**不可能**影响 token 内容，只影响数量？
期望答案：`MAX_NEW_TOKENS` 只控制 `generate_greedy` 的 while 循环次数（L665），不参与任何数值计算；模型的每一步推理与前几个 token 完全相同。

## 二、实验 B：有害改动 —— 故意改坏 `q_shifts[0]`（60~90 分钟，今天的重头戏）

### 改动内容

`q_shifts[0]`（main.c 约 L108，当前 `13u`）→ 改为 `12u`

### 第一步：写预判（教学 AI 用提问引导，不给答案）

引导问题链：
1. 右移从 13 位变 12 位，第 0 层 Q 的数值会放大还是缩小？几倍？（放大 2 倍）
2. INT8 的范围是多少？放大会怎样？（-128~127，饱和截位）
3. 第 0 层 Q 错了，后面的注意力、FFN、最终 token 会怎样？（逐层污染，输出乱）
4. 程序会崩溃吗？（**复习第 1 天盲区**：不会崩，硬件照常跑，数据悄悄坏）

期望预判成文："第 0 层 Q 放大约 2 倍并饱和截位 → 注意力分布异常 → 首 token 大概率不再是 ID 0（或后续 token 全乱）；程序不会死机，现象是'能跑但乱说'。"

### 第二步 A：Python 仿真预演（Track B 必做；Track A 也建议先做）

用 Q30 参考脚本做"改坏预演"——**不改 Python 文件，用命令行参数**：

```powershell
# 基线跑（默认 shifts），记录输出
python python\nanoGPT\tools\export_hardware_exact_hls_full.py

# 改坏跑（q_shifts[0] 13→12），记录输出
python python\nanoGPT\tools\export_hardware_exact_hls_full.py --q-shifts "12,12,12,12,12,12"
```

- 两次输出目录不同（`--out-dir` 可指定，建议第二次用 `...\hardware_exact_hls_full_broken`），对比产物中的 `argmax_tokens.mem` / JSON 里的 `argmax_first32`。
- **通过标准**：两次 token 序列出现可见分歧；用户能指出第一个分歧位置和"哪一步算坏"的因果链。
- ⚠️ 注意：脚本默认 `--quality-root` 指向 `fpga\nano_gpt\generated\int8_hw_ppl_pass_s256_d384_l6`，教学 AI 先确认该目录在当前工作区存在；不存在则在工程内搜索 `int8_hw_ppl_pass` 或 `weights.bin` 的实际位置并用 `--quality-root` 显式指定。找不到就跳过仿真，如实记录。

### 第二步 B：改 `main.c` 并走完流程

1. 改 `q_shifts[0]` 为 `12u`。
2. 重编 ELF → 重打包（BIF 改 ELF 路径）→（Track A：烧录）。
3. **Track A 观察**：`1:ROMEO:` 看首 token 是否还是 `0`；再用 `ps\scripts\dump_layer0_hello_output.tcl` 或 `dump_context_row_stages.tcl` dump 第 0 层中间数据，找到异常证据。
4. **Track B 观察**：以 Python 仿真结果为准，板级记录"待验"。

### 第三步：恢复与基线复验（不过这一步今天不算完）

1. 把 `q_shifts[0]` 改回 `13u`（或从 `.bak` 恢复，**推荐让用户手动改回**，多练一次）。
2. 重编 → 重打包 →（Track A：烧录）。
3. **基线复验**：`1:ROMEO:` 首 token 回到 ID `0`；Track B 则重跑一次默认参数的 Python 仿真确认与基线一致。
4. Word 记录五要素必须齐全：改了哪一行、预判原文、实际现象（仿真数据或板级 dump）、原因分析、恢复验证。

✅ 复述检查点：用户能用一句话总结今天的核心教训——"**shift 差 1 位，数值差 2 倍，模型不会死但会乱说；改代码的底气来自备份、仿真和基线复验。**"

## 三、收尾对比（讲 10 分钟）：实验 A 和 B 的本质区别

带用户做一张对比表（让他自己填）：

| | 实验 A（token 数） | 实验 B（shift 表） |
|---|---|---|
| 碰没碰数值计算 | 没碰 | 碰了 |
| 预判难度 | 必然正确 | 需要量化链路知识 |
| 坏掉的"症状" | 不会坏 | 能跑但输出乱 |
| 定位手段 | 看字符数 | 看 token 序列/dump 中间层 |

**教学点睛**：工程师眼里的改动分两类——"改行为"（A 类，安全）和"改数值"（B 类，危险）。B 类改动必须经过仿真/基线双重验证。第 5 天起的所有改动都是 B 类或更复杂。
