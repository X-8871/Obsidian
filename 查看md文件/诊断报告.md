## 1. 结论速览

1. **P2（PL 时钟只有 50 MHz）根因已完全证明**：QSPI 里 5 个 BOOT.BIN **全部**打包了 2019 年课程项目的旧 FSBL（`led_qspi_sd.sdk\fsbl\Debug\fsbl.elf`）。旧 FSBL 的 `ps7_init` 把 IO_PLL 设为 1000 MHz、FCLK0 分频 5×4 → **50 MHz**；而当前设计要求 IO_PLL 1800 MHz、6×3 → **100 MHz**。板上实测寄存器（`IO_PLL_CTRL=0x0001E008`、`FPGA0_CLK_CTRL=0x00400500`）与旧 ps7_init 的写入值逐位吻合。
2. **P1（QSPI 启动输出错误而 JTAG 正确）的最可能机制**：旧 FSBL 带来的不只是时钟差异——它把整块 SoC 按 2019 课程板配置：DDR 控制器（DDRC）13 个寄存器（含 DRAM 时序与 PHY/ODT 参数）与当前设计不同，MIO 引脚表、UART1、外设时钟分频也全部来自旧设计。JTAG 流程执行的是**当前设计的 ps7_init**（100 MHz + 当前 DDRC），所以同一份权重/模型在 JTAG 下正确、在 QSPI 下出错。
3. **已排除的假设**（有硬证据）：8 个数据分区在全部 5 个 BIN 中与当前源文件逐字节一致；PS ELF 就是当前 psuart 版（0x100000 入口）；`main.c` 无任何 JTAG 专属初始化、无 cache 操作（不存在 cache 一致性问题）。
4. **修复**：`BOOT_fix_20260820.bin`（**v2**）= 正确的 FSBL（来自当前 xsa 的平台构建，字节级验证内嵌当前 ps7_init）+ 与 BIN#5 完全相同的 bitstream/数据分区 + **UART 补丁版 PS 应用**（见 §3.7）。11 个分区自检 ALL PASS。
5. **交接提示词中"DIVISOR1→2"的修复方案被取代**：运行时改分频只能修时钟一个症状；正确做法是换用包含当前 ps7_init 的 FSBL，一次性修正时钟 + DDRC + MIO/外设配置。
6. **追加发现并已修复（v2）**：当前设计的 PS 配置未使能任何 MIO 外设（`PCW_UART1_PERIPHERAL_ENABLE=0`），当前 FSBL 不配置 UART1，而原 PS 应用的 `uart_init()` 是空函数——串口完全依赖旧 FSBL 的遗留配置（SLCR 在系统复位下保持）。**完整断电冷启动后串口会哑掉**。已在 PS 应用内补上完整的 UART1 自带初始化（MIO48/49 复用 + 参考时钟 + 波特率）并重建镜像（§3.7）。

## 3. 证据链

### 3.1 Step A —— 5 个 BOOT.BIN 的逐分区取证

方法：`bootgen -arch zynq -read` 解析每个 BIN 的镜像头/分区头表（分区偏移与长度字段按 32-bit 字计，×4 得字节），从原始 BIN 中切出全部 11 个分区，逐一 SHA256，与磁盘上的所有候选源文件比对。bitstream 分区先做 32-bit 字内字节序反转（bootgen 的变换，经验证：同步字 AA995566 在 BIN 中存为 66 55 99 AA），再与 `.bit` 载荷比对；ELF 分区按其 PT_LOAD 段的 paddr 跨度镜像（段间空隙补零）重建后比对。

结果（`evidence\partition_matrix_old_bins.csv`）：

| 分区 | 5 个 BIN 的内容 |
|---|---|
| [bootloader] fsbl.elf | **全部 = 2019 课程 fsbl.elf**（PT_LOAD SHA256 `7971C21B...`，98,312 B） |
| system.bit | BIN#1–#4 各含一个互不相同的旧 bitstream（磁盘上无对应 .bit）；**BIN#5 = 当前 qkt8 system.bit**（2026-08-20 01:01）字序反转载荷 + 4 B 尾填充，分区哈希 `8A1C8D3E...` |
| ps_mailbox_runner_psuart_entry100000.elf | 全部 = 当前 psuart ELF（PT_LOAD SHA256 `801B0460...`，10,696 B，load/exec 0x100000） |
| 8 个数据分区 | **全部与当前源文件逐字节一致**（weights `0F6B6BF5...`、scales `297D48D7...`、token_emb `E8736846...`、pos_emb `5523BF12...`、tok_scale `7DB262C6...`、pos_scale `47F72D47...`、layernorm `238232B4...`、lm_head_scale `D52AA81A...`），加载地址与 BIF 一致 |

> 结论：**数据与 PS 程序无罪**。5 个 BIN 之间唯一的差异是 bitstream（PL ROM/RTL 迭代：lmhead→romdiag→romconst→allparams→attention），以及共同的错误 FSBL。

### 3.2 Step B —— 板上烧的是哪个 BIN（推断）

- 离线无法直接得知，但可推断：**最可能是 BIN#5（attention_fixed）**——它是最后一次构建（01:01:51），且交接材料的时间线以它为最后尝试。
- 板上寄存器证据只能证明"旧 FSBL 在位"（5 个 BIN 都满足），不能区分 bitstream 代际。
- 上板判别方法（清单 §7）：读 `0x40000094`（构建标记，当前 RTL = `0x46584632`"FXF2"）与 `0x40000054`（`FULL_CONFIG_VERSION=0xF1171180`）。若读到的不是这两个值，说明 QSPI 里是更老代际的 bitstream（BIN#1–#4 之一）。
- 注意：曾尝试在 bitstream 内直接搜索这两个常量（`evidence\bitstream_marker_search.ps1`），全部未命中——属预期：它们是 RTL 逻辑常量，被综合进 LUT，不以原始字节形式出现在比特流中。该阴性结果本身不构成证据，仅说明此路不通。

### 3.3 Step C —— 时钟链解码与新旧 ps7_init 差异

AX7Z020 PS 晶振 33.333 MHz。两份 ps7_init 的关键写入：

| 寄存器 | 旧课程 FSBL | 当前设计 | 效果 |
|---|---|---|---|
| IO_PLL_CTRL 0xF8000108 `[18:12]`=FDIV | 0x1E (30) → 1000 MHz | 0x36 (54) → 1800 MHz | PLL 主频 |
| FPGA0_CLK_CTRL 0xF8000170 | `0x00400500`：SRCSEL=IO_PLL，DIVISOR=5，DIVISOR1=4 → **50 MHz** | `0x00300600`：SRCSEL=IO_PLL，DIVISOR=6，DIVISOR1=3 → **100 MHz** | PL 时钟 |
| ARM_PLL / DDR_PLL | FDIV=0x28 / 0x20 | 相同 | CPU/DDR 主频两边一致 |

板上实测 `0x0001E008` 的 `[18:12]`=0x1E、`0x00400500` 与旧 ps7_init 的 EMIT_MASKWRITE 序列逐位一致（0x8 是 ps7_init 掩码写不触碰的保留/复位位）。**→ 板上正在运行旧 FSBL 的 ps7_init，P2 根因坐实。**

**JTAG 与 QSPI 的环境不对称**（P1 的关键）：
- JTAG 部署脚本 `deploy_fx2_cold_jtag.tcl` 执行 `ps7_init.tcl`（位于 `workspace_manual_2026_1\ps_mailbox_runner\_ide\psinit\`，25,544 B，2026-08-09）——即**当前设计** ps7_init 的 tcl 孪生体：`mask_write 0xF8000108 ... 0x00036000`、`mask_write 0xF8000170 0x03F03F30 0x00300600` → 100 MHz + 当前配置。
- QSPI 启动执行的是镜像里 FSBL 自带的 ps7_init → 旧配置（50 MHz 等）。
- 因此"JTAG 正确 / QSPI 错误"的对照实验恰好证明了：**问题出在 PS 初始化环境的差异，而不是模型文件本身**。

**旧 FSBL 额外写入、当前设计完全不写的寄存器**（寄存器集合差异统计：旧 178 个、新 110 个）：
- MIO_PIN_00..53（0xF8000700–0xF80007D4）+ 0xF8000830：整张 2019 课程板的 MIO 引脚复用/电气配置；
- UART1 寄存器组（0xE0001000/1004/1018/1034）与外设时钟分频（0xF8000138/140/14C/150/154，按 1000 MHz IO_PLL 配的倍频）；
- GPIO（0xE000A008/A244/A248）等。

**DDR 控制器（0xF8006xxx）差异**（两边各 240 条写入，其中 13 个寄存器取值不同）：

| 寄存器 | 旧 | 新 | 含义 |
|---|---|---|---|
| 0xF8006000 ddrc_ctrl | 0x80/0x81 | 0x84/0x85 | 控制器模式位 |
| 0xF8006004 two_rank_cfg | 0x1081/0x81081 | 0x1082/0x81082 | rank/页策略 |
| 0xF8006014 dram_init_param | 0x0004281B | 0x0004285B | 初始化参数 |
| 0xF8006018 / 0xF800601C | 0x44E458D2 / 0x720238E5 | 0x44E458D3 / 0x7282BCE5 | **DRAM 时序** |
| 0xF8006030 | 0x00040930 | 0x00040B30 | 地址映射 |
| 0xF800603C / 6040 / 6044 | 0x777 / 0xFFF00000 / 0x0F666666 | 0x666 / 0xFFFF0000 / 0x0F555555 | **PHY/ODT/驱动强度** |
| 0xF8006120 / 6124 | 0x40000001 | 0x40000000 | PHY 相关 |

→ 旧 FSBL 用 2019 年工具链/板级预设的 DDR 时序与 PHY 参数初始化同一颗 DDR3。FSBL 自己读写 DDR 没问题（它按自己的参数训练），但 PL 通过 AXI HP 读权重/KV cache 时工作在"另一套"DDR 配置 + 半频 PL 时钟下——这正是"能跑、但结果微妙地错"的典型温床。

### 3.6 Step F —— PS 侧源码审查（排除 JTAG 依赖）

审查 `workspace_manual_2026_1\ps_mailbox_runner\main.c`（901 行）与 `startup.S`：
- 入口逻辑：`main()` 读 mailbox word2，为 0 则进入 `uart_console()`（QSPI 场景）——无 JTAG 前提；
- 地址常量与 BIF 一致：PL 0x40000000、UART1 0xE0001000、mailbox 0x00020000、weights 0x11000000、embeddings/LN/LM-head 各就各位；

- JTAG 加载脚本（`deploy_fx2_cold_jtag.tcl`、`load_bittrue_ps_params.tcl`、`load_ps_ddr_embedding_tables.tcl`）加载的文件与地址和 BIF 完全同源同址（`reference\...` 下的同一批 bin）。

### 3.7 追加发现与修复 —— UART1 冷启动缺口（BOOT_fix v2）

**发现经过**：核对"QSPI 与 SD 启动差异"时顺带检查了当前设计的外设使能位，发现 `ps7_parameters.xml` 中 `PCW_QSPI/SD0/UART1_PERIPHERAL_ENABLE` 全部为 0——当前 ps7_init **不写任何 MIO 引脚、不配置任何外设时钟**。再查 `main.c`：`uart_init()` 只有一条 `barrier()`，应用从不配置 UART。

**推理**：
- 旧课程 FSBL 启动时完整配置了 UART1（MIO 复用、参考时钟、控制器寄存器、波特率），所以旧镜像 QSPI 启动串口正常；
- JTAG 实验用的是当前 ps7_init（不配 UART）却仍有串口输出，是因为 **SLCR 寄存器在系统复位（非掉电）下保持**——JTAG 会话继承了此前旧 FSBL 启动写入的 UART 配置；
- BOOT_fix v1（当前 FSBL）在**完整断电冷启动**后：SLCR 全部复位 → 无人配置 UART1 的 MIO 复用（默认 GPIO）与参考时钟门控 → 串口无任何输出，验收无法进行。

**修复**：把 UART1 初始化补进 PS 应用的 `uart_init()`（应用自己保证控制台可用，不依赖 FSBL）：

| 步骤 | 寄存器 | 值 | 依据 |
|---|---|---|---|
| SLCR 解锁 | 0xF8000008 | 0xDF0D | TRM 固定序列 |
| MIO48 = UART1_TX | 0xF80007C0 | 0x000012E0 | 与旧 ps7_init 逐字段一致（L3_SEL=7、LVCMOS18、上拉） |
| MIO49 = UART1_RX | 0xF80007C4 | 0x000012E1 | 同上 |
| UART1 APB 时钟门控 | 0xF800012C bit21 | 置 1 | 旧 ps7_init 的 APER_CLK_CTRL |
| UART 参考时钟 | 0xF8000154 | 0x00001202（DIVISOR=18） | 1800 MHz ÷ 18 = **100 MHz**（与旧环境 1000÷10 等效） |
| SLCR 上锁 | 0xF8000004 | 0x767B | TRM 固定序列 |
| 控制器 | 0xE0001000/1004/1018/1034 | 控制 0x17、模式 0x20（8N1）、CD=124、BDIV=6 | 100 MHz/(124×7)=115207≈115200，与旧 FSBL 相同 |

**勘误**：取证早期曾把 `0xF800014C` 凭记忆标为 UART_CLK_CTRL，实际 `0xF800014C = LQSPI_CLK_CTRL`（QSPI 参考时钟，旧值 DIVISOR=5 → 200 MHz），UART 参考时钟在 `0xF8000154`。错误解读（"UART 参考 200 MHz"）会与现场 115200 波特矛盾，已按工具生成的寄存器表纠正；未进入任何产物。若按错误地址写 DIVISOR，改到的将是 QSPI 读取时钟，后果严重——此勘误特此记录。

**重建与等价性验证**（`evidence\uart_patch\`）：
- 源：`workspace_manual_2026_1\ps_mailbox_runner\main.c` 原样拷贝，仅替换 `uart_init()` 函数体；工具链 arm-none-eabi-gcc 13.4.0（Vitis 2026.1 自带），-O2、`lscript.ld` 入口 0x100000、`--build-id=none`、strip --strip-debug；
- 与同源码 control 版逐函数对比：**20 个函数中 19 个指令数完全一致，仅 `main` +27 条**（uart_init 内联进 uart_console→main）；补丁指令序列（movw 0xDF0D/0x767B/0x12E0/0x12E1 等）在反汇编中确认；
- 新 ELF：入口 0x100000，单 PT_LOAD 跨度 7,736 B，span SHA256 `41451323...`，文件 SHA256 `FD6680E7...`；
- **配对约束**：DIVISOR=18 假定 IO_PLL=1800 MHz。此 ELF 只可与 BOOT_fix/当前 ps7_init 环境配对（旧 FSBL 的 1000 MHz 环境下波特率会错）——BOOT_fix v2 满足该条件；
- v2 镜像重打包后 11 分区自检再次 ALL PASS（`self_check\fix_bin_partitions_v2.csv`）。

## 6. 新手解释（为什么）

**Q1：为什么一个"旧的 FSBL"会把时钟改成 50 MHz？FSBL 不是只负责加载吗？**
FSBL（First Stage Boot Loader）是 BootROM 之后第一段在 PS 上跑的代码。上电后 PLL/DDR/MIO 全都处于复位默认态，CPU 降速运行；FSBL 里的 `ps7_init` 负责把 SoC 配置成硬件设计假定的样子：锁 PLL、配 DDR、设 MIO 引脚、最后才加载 bitstream 和应用。关键点：**ps7_init 的内容是在 Vivado 导出硬件（xsa）时按你的 Block Design 生成的，然后编译进 FSBL**。也就是说 FSBL 和 bitstream 是"一对"——bitstream 假设 PL 时钟是 100 MHz，配套的 FSBL 就会把 FCLK0 配成 100 MHz。这次 5 个 BIN 错把 2019 年 LED 课程的 FSBL 和 2026 年的 nanoGPT bitstream 配成了一对：bitstream 按 100 MHz 设计，FSBL 却只给 50 MHz。

**Q2：为什么 JTAG 调试时一切正常，QSPI 启动就错？**
JTAG 流程（xsdb）在加载 bitstream 前会执行**当前 xsa 生成的 ps7_init + ps7_post_config**——等于每次 JTAG 运行都重新做一遍"正确的"PS 初始化（100 MHz、当前 DDR 参数）。而 QSPI 独立启动时没有任何外部干预，PS 初始化完全由镜像里的 FSBL 决定——也就是那份旧课程的配置。所以同一块板、同一份模型文件，两条路径跑在两个不同的"电气环境"里。这也是为什么"JTAG 验证通过"不能替代"QSPI 启动验证"。

**Q3：50 MHz 只是慢一倍，为什么输出会"错"而不是"慢但正确"？**
纯数字同步逻辑降频运行通常确实只是变慢。但这里降频只是旧 FSBL 带来的差异之一：它还用 2019 年的参数初始化了 DDR 控制器（时序、驱动强度、ODT 都不一样），并按旧板子的设定配置了 MIO 与外设时钟。PL 读权重/KV cache 要走 AXI→DDR 控制器→DDR3 这条链，链条两端的配置必须一致；"PS 侧按 A 套参数训练、PL 侧设计假设 B 套参数 + 时钟关系也变了"就可能出现偶发的数据边缘错误。这类错误的典型表现恰恰是"大体正常、细节发散"——正合"第 1 token 对、第 2 token 起错"（第 2 个 token 开始依赖 K/V cache 的写后读）。

**Q4：bootgen 的 BIN 里到底装了什么？**
Zynq 的 BOOT.BIN = 引导头 + 若干"分区"：`[bootloader]` 分区是 FSBL（BootROM 把它搬进 OCM 执行）；其后依次是 bitstream（FSBL 经 PCAP 送入 PL）、PS 应用 ELF（FSBL 搬到 DDR 并跳转）、以及任意多个 `[load=地址]` 数据分区（FSBL 原样搬到指定 DDR 地址）。每个分区在头表里记录加载地址、偏移和长度（按 32-bit 字计）。我们做的取证就是把头表解析出来、按偏移把每个分区切回原始字节，再和源文件比哈希——所以"5 个 BIN 的数据都对、FSBL 都错"这个结论是逐字节成立的。

**Q5：为什么 .bit 烧进 BOOT.BIN 后字节顺序变了？**
bootgen 会把比特流载荷按 32-bit 字做字节序反转（AA 99 55 66 存成 66 55 99 AA），这是为了让 PCAP DMA 按字推送时比特流保持正确语义。比对时必须先做同样的字内反转再哈希，否则会误判"bitstream 不匹配"（我们最初就栽在这里，后用同步字验证了变换规则）。
