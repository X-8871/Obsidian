# 大文件清单式原子同步验收 SOP

> [!IMPORTANT]
> 本 SOP 适用于“客户端提交完整文件清单，服务端只上传差异并原子切换 revision”的同步系统。验收目标不是证明接口能返回 200，而是证明失败不会破坏上一完整版本、字节进度真实连续、权限边界有效。

## 一、输入与前置条件（Inputs）

### 1.1 必备环境

- 一个隔离的测试账号和一个无权限对照账号。
- 一个小型测试目录，以及一个接近真实规模的目录。
- 至少一个大于“小文本批处理阈值”的文件，建议同时准备 10～50 MiB 和接近单文件上限的样本。
- 可观察服务端正式对象、staging、数据库 revision、服务日志、反向代理日志和资源占用。
- 明确两种产品语义：
  - **覆盖模式（A）**：提交后正式集合与本次 manifest 完全一致。
  - **新建模式（B）**：创建新的独立目录或 Vault，不改变旧集合。

### 1.2 测试样本

```text
sync-fixture/
├── README.md                 # 可修改文本
├── rename-before.md          # 用于重命名
├── delete-me.txt             # 用于删除
├── assets/image.png          # 图片
├── assets/document.pdf       # PDF
├── assets/media.mp3          # 音频或视频
├── diagrams/sample.canvas    # 结构化文本
└── binaries/large.bin        # 大文件或未知二进制
```

测试前记录每个文件的相对路径、字节数、mtime 和 SHA-256。不得使用包含密码、令牌或个人隐私的真实文件做公开日志样本。

### 1.3 成功判据

- 正式版本只能在完整校验后一次切换；失败 run 不改变上一 revision。
- 上传字节进度单调递增，重试不倒退、不重复累计。
- 服务端以真实流重新计算大小和 SHA-256，不信任客户端声明。
- 用户、设备和签名 URL 均不能越权读取其他主体的数据。

## 二、执行阶段

### Phase 1：建立只读基线

1. 记录当前正式 revision、文件数、逻辑总字节和对象数量。
2. 记录服务端磁盘、内存、端口和日志基线。
3. 确认上一个正式版本可完整列出、打开和下载。
4. 确认客户端排除规则与单文件上限符合产品定义。

输出：`baseline-revision`、manifest 摘要、资源基线和可回滚点。

### Phase 2：B 模式新建小型集合

1. 用测试账号提交完整 manifest。
2. 核对服务端返回的新增、变化、未变化和删除集合。
3. 上传小文本、结构化文本和至少一种二进制附件。
4. commit 后确认生成新的独立集合，旧集合内容和 revision 不变。
5. 在读取端打开所有支持类型；未知文件至少显示元信息并允许下载。

失败判据：覆盖了旧集合、重名未隔离、附件空白且无错误提示、commit 前正式列表已变化。

### Phase 3：A 模式覆盖与增量差异

对已存在集合做以下四类变化：

1. 修改 `README.md` 内容。
2. 新增一张图片。
3. 删除 `delete-me.txt`。
4. 把 `rename-before.md` 重命名为 `rename-after.md`。

重新扫描并提交完整 manifest，核对：

- 只有新增和哈希变化的文件进入上传列表。
- 未变化文件不重复上传。
- 删除由服务端比较完整 manifest 得出，不接受客户端单独声明的 removed 集合。
- 重命名按“一条删除 + 一条新增”或协议定义的等价方式生效。
- commit 后 revision 只增加一次，最终集合与客户端目录逐路径一致。

### Phase 4：大文件流式上传与进度

1. 选择大于批处理阈值的文件，记录真实字节数。
2. 启动上传并每隔固定时间记录：已扫描字节、已上传字节、速度、当前文件和百分比。
3. 在上传中途触发一次可恢复网络中断，观察重试。
4. 上传完成后比较客户端、staging/正式对象和下载结果的 SHA-256。

必须满足：

- 扫描和上传阶段都持续给出字节级反馈，不能只显示“文件 N/M”。
- 全局 `uploadedBytes` 单调不减，重试同一文件时不重复加上已失败尝试的字节。
- 服务端和反向代理不把整个文件缓冲进内存；活动期间资源占用低于服务限制。
- 客户端取消后停止后续文件，未 commit run 不影响正式 revision。

### Phase 5：原子性与故障注入

分别在以下位置中断一次：

1. begin 后、任何上传前。
2. 部分文件上传后、confirm 前。
3. 全部 confirm 后、commit 前。
4. commit 事务执行期间模拟数据库错误或磁盘不足。

每次中断后验证：

- 上一正式 revision 仍可读，文件集合和下载哈希不变。
- staging 可识别为未完成 run，不会被读取端当作正式对象。
- 重试或重新 begin 不会重复创建错误的正式 revision。
- 孤立对象清理不会删除仍被正式 revision 引用的对象。

### Phase 6：认证、授权与签名边界

1. 无登录令牌访问列表、配对、上传准备和签名接口，应返回 401。
2. 对照账号访问测试账号的集合、文件 ID、run ID 或设备，应返回 403/404 且不泄露存在性细节。
3. 篡改相对路径为 `../`、绝对路径、反斜杠绕过或编码变体，应被拒绝。
4. 篡改上传 token、文件大小或 SHA-256，confirm/commit 必须失败。
5. 签名 URL 过期后不可下载；合法 Range 请求应返回正确字节区间。
6. 撤销设备后，其令牌不能继续同步；一次性配对码不能复用。

### Phase 7：渲染、移动端与运行资源

1. 验证 Markdown、内部链接、图片、图表、Canvas、PDF、音视频和未知二进制。
2. 验证移动端、深色模式、刷新、重新登录和离线缓存恢复。
3. 核对应用日志、反向代理日志和错误响应，不得含 Authorization、Cookie、上传 token、签名密钥或正文。
4. 记录磁盘增量、对象去重效果、服务峰值内存和空闲退出行为。
5. 如使用按需激活服务，按 [[低内存Node服务按需激活与原子发布指南]] 验证 socket/service 状态。

## 三、输出物标准与验收清单（Acceptance Checklist）

### 3.1 必须留存的脱敏证据

- 测试时间、版本提交、客户端版本和服务 release。
- 初始与最终 revision、文件数、逻辑字节数和实际上传字节数。
- 大文件进度采样和最终 SHA-256 对比结果。
- A/B 模式最终路径集合差异。
- 故障注入点与“旧 revision 仍可读”的证据。
- 认证、越权、路径穿越、签名过期和设备撤销的状态码摘要。
- 峰值内存、磁盘余量、空闲退出和日志脱敏检查结果。

### 3.2 完成清单

- [ ] B 模式创建独立集合，不影响旧数据。
- [ ] A 模式新增、修改、删除、重命名全部正确。
- [ ] 未变化文件不重复上传。
- [ ] 大文件字节进度连续、单调，取消和重试正确。
- [ ] 服务端重新校验真实大小与 SHA-256。
- [ ] 四个故障注入点均未破坏上一 revision。
- [ ] 用户隔离、路径校验、签名过期、Range 和设备撤销通过。
- [ ] 所有声明支持的查看器通过，未知文件可下载。
- [ ] 日志不含凭据、签名、token 或正文。
- [ ] 资源限制、磁盘余量和回滚路径通过。
- [ ] 只有真实数据验收全部通过后，项目状态才可标记为“迁移完成”。
